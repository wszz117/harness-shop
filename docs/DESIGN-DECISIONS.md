# 设计决策记录

> 写给架构师和技术评审。每条记录回答四个问题：遇到了什么问题、决定怎么做、放弃了哪些方案、要付出什么代价。ADR-1 至 ADR-4 的完整论述见 [架构总览 7.2 节](architecture/architecture-overview.md#72-关键架构决策记录adr-摘要)，这里只列出要点；ADR-5 起为本文新增。

## 一览

| 编号 | 决策 | 一句话理由 |
|------|------|-----------|
| ADR-1 | 演示域选 MERN | 物理目录边界清晰，门禁可以用简单的静态扫描实现 |
| ADR-2 | 门禁用 Shell/Python 脚本 + 退出码 | 本地、hooks、CI 三处运行同一份脚本，口径一致 |
| ADR-3 | 复核结果写文件，不注入对话 | 持久化事实不会被上下文稀释，并可归档 |

| ADR-7 | 流程分三档 | 防止严格流程因为“太麻烦”被整体弃用 |

## ADR-1 至 ADR-4（要点）

**ADR-1 演示域选 MERN。** 目的是验证框架而不是展示技术栈。routes/controllers/services/models 的物理分层让“架构一致性”可以靠目录与 import 扫描完成；放弃了 Next.js 等同构框架，因为服务端与客户端边界模糊会显著提高门禁实现成本。

**ADR-2 门禁用脚本与退出码。** 门禁的检查对象包括目录结构、文档完整性、证据存在性，超出了 ESLint 一类 AST 工具的范围。代价是脚本需要按技术栈改写，这部分在 [移植指南](../.harness/multi-repo-adaptation.md) 中单列为“需要重做”。

**ADR-3 复核结果写入 `.hook-results/`。** 项目经理角色读取的是文件，不是对话中的转述；文件可以归档进证据链；会话重启后结果仍在。

**ADR-4 编号永不复用。** 退役编号进入退役列表，`spec-lint.py` 校验全库唯一。代价只是一个 Markdown 列表。

## ADR-5 用多个职责分离的角色，而不是一个全能代理

**问题。** 同一个代理既写代码又审代码时，会倾向于为自己的实现辩护（自审失效）。

**决定。** 拆成 7 个角色，每个角色有契约文件写明“能做什么、不能做什么”：开发不审自己的代码，测试不改被测代码，项目经理只调度不产出。角色之间只通过文件交接。

**放弃的方案。** 单一代理加“请认真自查”的提示词。实践中这类提示会随对话变长而被稀释。

**代价。** 交接文档变多，单个任务耗时增加。ADR-7 的分档用来控制这部分成本。

## ADR-6 人工只设两个关口

**问题。** 人工审核放得太多，人会变成瓶颈；放得太少，又失去控制。

**决定。** 只设两处：动手写代码之前（审需求与方案，此时改方向的成本最低），以及验收时（此时证据最完整，人只需要做判断，不需要读代码）。

**放弃的方案。** 每个阶段都人工确认；或者完全自动、只在最终合并时审核。前者让人成为瓶颈，后者让方向性错误拖到最后才被发现。

**代价。** 两个关口之间的质量完全依赖自动复核的覆盖面。v1.1 的复核记录说明，这个覆盖面需要持续补强（见 ADR-8 至 ADR-10）。

## ADR-7 流程分三档

**问题。** 改一个错别字也要七个角色接力，团队会因为嫌麻烦而整体弃用流程。

**决定。** 快速档（跳过部分环节）、标准档、加固档（额外做影响面分析）。档位在提案中显式勾选，并由门禁检查所需文档是否齐全。

**代价。** 档位选择本身依赖人的判断，存在“把大改动标成快速档”的可能。目前靠第一个人工关口把关。

## ADR-8 收工复核中加入真实启动检查（v1.1）

**问题。** v1.0 中汇率服务的单测全部通过、文档写着 PASS，但服务启动时没有接上定时刷新，接口一直返回 503。单测只验证了“零件”，没有验证“组装”。

**决定。** `backend-smoke.sh` 在空闲端口真实启动后端，请求 API 根路径和汇率接口，汇率接口必须返回 200。该脚本作为收工 hook 的第五项检查，失败即判定不通过。

**放弃的方案。** 只在 CI 中跑端到端测试。CI 是事后验证，AI 已经提交了“完成”的汇报；收工时就拦下来，返工成本更低。端到端测试需要浏览器和完整数据，放进每次收工会太慢。

**代价。** 每次收工多一次真实启动（本地实测整轮复核约 12 至 18 秒），并且需要本机有 MongoDB。端口被占用等环境问题会降级为警告，避免误判。

## ADR-9 用通过用例数做质量基线（v1.1）

**问题。** 原基线只统计测试文件数量，而且统计脚本只看顶层目录，漏掉了子目录中的测试，导致复核程序在任何情况下都判失败，失去了可信度。另外，删掉一个测试文件中的部分用例也不会被发现。

**决定。** 测试文件改为递归统计；收工 hook 额外比较“本次通过用例数”与基线中的 `min_pass`，低于基线即判失败。

**放弃的方案。** 用代码覆盖率做基线。覆盖率对重构和删除死代码过于敏感，误报多；用例数简单、稳定，正好对准“删测试凑绿”这一类问题。

**代价。** 拦不住“空断言”测试（用例存在但什么也没验证）。已列入 Roadmap：增加断言数基线。

## ADR-10 证据截图做真实性校验（v1.1）

**问题。** v1.0 的测试报告引用了 4 张截图，文件都存在，但都是 1×1 像素的占位图。只检查“文件存在”的证据校验形同虚设。

**决定。** `check-e2e-evidence.py` 要求截图宽高不小于 200 像素、文件不小于 5 KB，并纳入 `check-harness.sh` 对归档任务做检查。截图由端到端测试在断言通过后自动保存，不允许手工放置。

**代价。** 阈值是经验值，无法证明截图内容与场景相符。内容相符目前由测试报告中的“场景 ↔ 截图”对照表和人工验收把关。

## ADR-11 汇率刷新失败立即降级

**问题。** v1.0 的设计是刷新失败后仍显示“正常”，直到缓存过期才切换为“缓存”状态。这段时间里，用户看到的状态与真实状态不一致。

**决定。** 刷新失败时保留上次成功的汇率并立即标记为“缓存”，前端显示黄色提示；没有任何可用汇率时只显示美元价格，下单不受影响。规格、需求、设计、代码与测试统一为同一份四态契约（正常 / 缓存 / 不可用 / 加载中）。

**代价。** 上游偶发失败会更频繁地出现提示条。对一个只做“参考价”的功能，准确比安静更重要。
